01 · Contexto e solução

Introdução

O Projeto Integrador consiste no desenvolvimento de um sistema desktop para organização e controle do acervo da biblioteca do Tiro de Guerra. A proposta surgiu de uma necessidade identificada junto aos responsáveis pela instituição: os registros de empréstimos e devoluções eram realizados manualmente, por meio de anotações físicas, o que dificultava o acompanhamento dos materiais e aumentava a possibilidade de inconsistências e perda de informações.

A biblioteca reúne obras utilizadas como apoio à formação e aos estudos dos integrantes do Tiro de Guerra. Nesse contexto, localizar um livro, identificar sua disponibilidade e saber com quem está emprestado são atividades que precisam de informações confiáveis e atualizadas. A ausência de um sistema centralizado tornava essas tarefas mais demoradas e dependentes da conferência de registros manuais.

Para responder a esse problema, o grupo propôs uma aplicação que concentra os dados do acervo e as operações de circulação em um único ambiente. O sistema foi desenvolvido em C#, utilizando Windows Forms para a interface gráfica e MySQL para persistência dos dados. Sua estrutura contempla autenticação, cadastro e consulta de livros, cadastro de atiradores e registro de empréstimos e devoluções.

O escopo foi delimitado à biblioteca. Outros setores do Tiro de Guerra, como fardamento, materiais logísticos e armamento, não fazem parte da solução, pois envolvem informações institucionais de natureza distinta e requisitos específicos de segurança. A decisão mantém o projeto concentrado em uma demanda concreta e permite desenvolver uma ferramenta compatível com a dimensão da biblioteca.

Objetivo central: digitalizar o controle do acervo, facilitar a localização das obras, acompanhar a circulação dos exemplares e reduzir falhas associadas ao registro manual.

Estado de desenvolvimento

O projeto já possui uma aplicação desktop em desenvolvimento, com módulos de login, cadastro, consulta do acervo e registro de empréstimos e devoluções. O banco relacional foi modelado no MySQL Workbench, e o cadastro contempla a localização física dos livros por prateleira.

Como próximos passos, estão previstas a integração com Google Books e Open Library para consultar dados pelo ISBN, melhorias nos níveis de acesso e ampliação dos relatórios. Essas funcionalidades ainda são etapas futuras.

02 · Organização e eficiência dos dados

Estrutura de Dados

A disciplina de Estrutura de Dados contribui para compreender como as informações podem ser organizadas, armazenadas, percorridas e recuperadas. No sistema da biblioteca, essa preocupação aparece no tratamento de livros, autores, usuários, exemplares e empréstimos, que precisam manter relações consistentes para que as operações administrativas funcionem corretamente.

A escolha de um banco de dados relacional MySQL estabelece a persistência das informações em tabelas relacionadas. Já na aplicação desenvolvida em C#, os registros podem ser representados por objetos e coleções em memória durante as operações realizadas pela interface. Essa combinação separa o armazenamento permanente dos dados da sua manipulação temporária pela aplicação.

Estruturas lineares: organização de registros e movimentações

O código utiliza coleções List<T> em C# para reunir autores, atiradores, empréstimos em aberto, registros do histórico e resultados de busca. Por serem dinâmicas, permitem adicionar, remover e percorrer elementos durante a execução.

Quando uma lista é percorrida para localizar ou filtrar um item, o custo no pior caso é O(n), pois pode ser necessário verificar todos os elementos.

Uma fila também oferece um modelo útil para representar solicitações que devem ser atendidas na ordem de chegada. Caso o projeto implemente futuramente reservas de exemplares, por exemplo, uma fila de espera poderá organizar os interessados por ordem de solicitação. É importante destacar que essa é uma possibilidade de evolução: a documentação atual descreve empréstimos e devoluções, mas não confirma a implementação de uma fila de reservas.

Da mesma forma, uma pilha poderia apoiar um histórico de ações administrativas ou uma função de desfazer operações, permitindo recuperar a ação mais recente antes das anteriores. Esse recurso não integra o escopo funcional documentado, mas demonstra como uma estrutura linear pode ser aplicada a uma necessidade futura de auditoria e recuperação de operações.

Ordenação e busca: localização eficiente do acervo

A consulta de livros por título, autor, categoria e disponibilidade é uma das funções centrais do sistema. A busca exige comparar os critérios informados pelo operador com os registros armazenados. Em uma coleção não ordenada, uma busca sequencial pode precisar verificar até n registros, resultando em complexidade linear O(n) no pior caso.

Quando os dados estão ordenados por uma chave compatível com a pesquisa, a busca binária pode reduzir o número de comparações para O(log n). Entretanto, ela depende de uma coleção previamente ordenada e de acesso adequado aos elementos. Por isso, não se deve afirmar que a aplicação já utiliza busca binária: no projeto atual, a recuperação dos registros é realizada a partir da integração com o banco de dados, e a estratégia concreta depende das consultas SQL e dos índices definidos.

No sistema, a ordenação do histórico é realizada por meio de consultas SQL com ORDER BY, que solicita ao banco de dados a apresentação dos registros conforme um ou mais campos. Portanto, a organização dos resultados já faz parte do fluxo de consulta, mas não foi identificada no código analisado uma implementação própria de algoritmo de ordenação, como Merge Sort ou Quick Sort.

Essa distinção é relevante para a análise de complexidade: quando a ordenação é delegada ao banco de dados, o custo depende do plano de execução, dos índices disponíveis, do volume de registros e do mecanismo de armazenamento. A busca binária continua sendo um exemplo teórico útil para comparação, mas não deve ser atribuída à aplicação sem evidência de sua implementação.

Estruturas avançadas: identificação e acesso aos registros

Tabelas hash são estruturas que associam uma chave a um valor e permitem, em condições adequadas, acesso médio próximo de O(1). No sistema, um identificador único para cada livro ou exemplar pode servir como referência para localizar um registro sem depender exclusivamente do título, que pode se repetir ou apresentar variações de escrita. O banco de dados relacional também pode garantir a unicidade desse identificador por meio de restrições apropriadas.

É importante diferenciar o conceito de tabela hash de uma tabela do MySQL: apesar do nome semelhante, são estruturas distintas. A tabela hash é uma estrutura de dados baseada em função de dispersão; a tabela relacional organiza registros em linhas e colunas. O projeto utiliza o MySQL como armazenamento persistente, e não há confirmação de que uma tabela hash tenha sido implementada diretamente na aplicação.

No MySQL/InnoDB, os índices são organizados em estruturas baseadas em B-tree. Chaves primárias e índices em campos pesquisados frequentemente ajudam a localizar registros, embora também tenham custo de manutenção em inserções e atualizações.

O identificador dos livros também contribui para a localização precisa dos registros. No sistema, o código segue o padrão LIV seguido de três algarismos, permitindo distinguir os livros por um código próprio em vez de depender somente do título, que pode se repetir. Esse identificador pode ser tratado como chave de pesquisa e, quando definido como único no banco, ajuda a preservar a integridade dos registros.

Embora tabelas hash possam oferecer acesso médio próximo de O(1) em cenários apropriados, não foi identificada uma implementação explícita de tabela hash no código analisado. Da mesma forma, filas e pilhas não devem ser apresentadas como estruturas já utilizadas: filas poderiam organizar futuras reservas por ordem de solicitação, e pilhas poderiam apoiar um histórico de ações com possibilidade de desfazer operações.

Contribuição da disciplina: Estrutura de Dados permite avaliar que não basta armazenar informações: é necessário escolher formas adequadas de organizá-las e recuperá-las. No PI, esse raciocínio orienta a modelagem relacional, a representação dos registros na aplicação e a análise de desempenho das consultas do acervo.

03 · Linguagens formais, validação e custo computacional

Teoria da Computação

A Teoria da Computação oferece modelos para compreender linguagens, reconhecer padrões, validar sequências de símbolos e analisar os limites de eficiência dos algoritmos. No sistema da biblioteca, esses conceitos se relacionam principalmente à validação dos dados inseridos, ao processamento das informações trocadas com serviços externos e à avaliação do custo das operações de busca e organização.

Validação léxica e autômatos finitos

O cadastro de livros recebe informações como título, autores, editora, ano de publicação, categoria e ISBN. Antes de persistir esses dados, a aplicação deve verificar se os valores respeitam formatos e regras esperadas. Expressões regulares permitem descrever padrões de caracteres, enquanto autômatos finitos determinísticos (AFD) oferecem um modelo formal para reconhecer cadeias que pertencem a uma linguagem regular.

Um exemplo diretamente relacionado ao projeto é o código de identificação dos livros, formado pelo prefixo LIV seguido de três algarismos. Esse padrão pode ser descrito pela expressão regular ^LIV[0-9]{3}$. A expressão reconhece cadeias que começam com as letras LIV e terminam com exatamente três dígitos, sem caracteres adicionais.

O mesmo padrão pode ser representado conceitualmente por um Autômato Finito Determinístico (AFD): o autômato percorre os símbolos esperados — L, I, V e, em seguida, três dígitos —, avançando de estado a cada símbolo válido e aceitando a entrada somente ao final da sequência correta. Esse exemplo mostra como um conceito formal pode explicar uma regra concreta de identificação do acervo. A expressão e o AFD são apresentados como formalização do padrão; não se afirma que exista um autômato implementado no software.

Outras validações também são pertinentes ao cadastro, como verificar campos obrigatórios, ano composto por dígitos e formato do ISBN. Essas regras podem impedir que entradas malformadas avancem para a persistência, mas a validação sintática não comprova, por si só, que a obra existe ou que os dados bibliográficos estão corretos.

Essas verificações ajudam a impedir que entradas malformadas avancem para as etapas seguintes do cadastro. A validação de formato, porém, não comprova por si só que a obra existe ou que os dados bibliográficos estão corretos; ela apenas verifica se a entrada atende às regras definidas. A documentação do projeto descreve o cadastro manual e prevê integração futura com APIs, mas não especifica quais expressões regulares ou AFDs foram implementados. Assim, esse é um fundamento técnico aplicável e um ponto que pode ser formalizado na evolução do software.

Análise sintática e estruturas hierárquicas

Na futura integração com Google Books e Open Library, o sistema poderá receber respostas em JSON, formato que organiza informações em objetos, propriedades e listas aninhadas.

Autômatos de pilha modelam linguagens que exigem acompanhar estruturas aninhadas, como o balanceamento de delimitadores. Na implementação, bibliotecas de JSON fazem a leitura e a conversão desses dados; não é necessário criar um autômato próprio.

Essa relação será importante quando forem integradas as APIs Google Books e Open Library, previstas para auxiliar o preenchimento dos dados bibliográficos a partir do ISBN. As respostas recebidas precisarão ser interpretadas antes de preencher os campos do cadastro. O processamento deverá considerar respostas incompletas, propriedades ausentes e tipos inesperados, evitando que uma falha na comunicação ou um dado inválido comprometa o registro. Como essa integração está planejada para uma etapa posterior, o processamento de JSON deve ser apresentado como aplicação futura dos conceitos, e não como recurso já concluído.

Complexidade, tratabilidade e análise de P versus NP

A análise de complexidade permite estimar como o custo de um algoritmo cresce conforme aumenta a quantidade de registros. No sistema da biblioteca, operações como pesquisar livros, ordenar resultados, listar empréstimos e gerar relatórios precisam continuar eficientes mesmo quando o acervo e o histórico de movimentações aumentarem.

Uma busca sequencial em uma coleção List<T> pode exigir a verificação de até n elementos, com custo O(n) no pior caso. A busca binária pode alcançar O(log n), desde que os dados estejam ordenados e a estrutura permita acesso apropriado. Algoritmos eficientes de ordenação por comparação costumam apresentar custo O(n log n). No sistema, a ordenação do histórico utiliza ORDER BY no SQL, enquanto os índices do MySQL/InnoDB apoiam a recuperação de registros. O desempenho real depende do plano de execução, dos índices, da quantidade de dados transferidos e da implementação das consultas.

O problema central do PI não exige, em seu escopo atual, resolver um problema combinatório complexo de otimização, como roteamento de grande escala ou alocação de recursos com restrições numerosas. As operações previstas — cadastro, consulta, empréstimo, devolução e relatórios básicos — são tratadas por regras determinísticas, coleções e consultas ao banco de dados. A análise relevante é acompanhar como o custo dessas operações cresce com o número de livros e movimentações, além de considerar o efeito dos índices e da ordenação realizada pelo SGBD.

A discussão sobre P versus NP ajuda a reconhecer a diferença entre problemas que podem ser resolvidos eficientemente e problemas para os quais não se conhece algoritmo polinomial geral. Não é correto afirmar que o projeto resolve um problema NP-completo ou que precisa de heurísticas para seu funcionamento atual. Caso uma evolução futura inclua distribuição otimizada de exemplares, priorização de reservas com múltiplas restrições ou planejamento complexo de recursos, será necessário avaliar formalmente o problema antes de escolher uma estratégia exata ou aproximada.

Contribuição da disciplina: Teoria da Computação fornece uma base para definir regras de validação, compreender o processamento de dados estruturados e justificar escolhas algorítmicas por meio da complexidade. Isso contribui para que o sistema não apenas funcione, mas trate entradas de maneira consistente e mantenha desempenho adequado à dimensão do acervo.

04 · Síntese do aprendizado

Considerações finais

O desenvolvimento do sistema para a biblioteca do Tiro de Guerra demonstra como conteúdos estudados em Engenharia de Computação podem ser aplicados na construção de uma solução para uma necessidade institucional concreta. A substituição dos registros manuais por uma aplicação integrada ao MySQL centraliza as informações, facilita a consulta do acervo e melhora o acompanhamento dos empréstimos e devoluções.

Estrutura de Dados contribui para compreender a organização dos registros, a representação das informações em memória e os diferentes custos envolvidos em operações de busca e ordenação. Teoria da Computação, por sua vez, oferece fundamentos para validar entradas, interpretar dados estruturados e analisar a eficiência dos algoritmos utilizados. As duas disciplinas se complementam: uma trata da organização e manipulação dos dados; a outra ajuda a compreender os padrões que esses dados devem respeitar e os limites computacionais das operações realizadas.

O projeto já evidencia aplicações concretas, como coleções List<T>, ordenação SQL com ORDER BY e índices do MySQL/InnoDB. O código LIV seguido de três dígitos permite demonstrar expressões regulares e AFD. A integração com APIs e o processamento de JSON são possibilidades de evolução.

Assim, o principal resultado do Projeto Integrador não se limita à criação de uma aplicação: consiste em transformar uma demanda real em uma solução planejada, modelada e desenvolvida com fundamentos de engenharia, conectando conhecimento acadêmico, análise de requisitos e aplicação prática.
